# Полный паритет клиента btawg на Windows x64

## Цель и границы

Добавить нативный `btawg-client.exe` для Windows 10 (22H2) и Windows 11 x64. Пользователь получает текущий Linux-клиент с тем же TUI, настройками, путями трафика и эксплуатационными операциями, а не новый клиент с урезанной функциональностью. Оба Linux-бинарника и существующий формат релиза Linux сохраняются. Windows-клиент использует обычный импорт `btawg://` с Linux-хаба; отдельные сервер, учётные записи, подсети, форматы импорта и протоколы не нужны. Поддержка старых импортов и несовпадающих версий хаба не расширяется и не сужается относительно Linux-клиента.

## Подходы

- **Общий Go-клиент, нативные границы Windows — выбран.** Один TUI, один клиентский протокол управления, общие движки, маршрутизация пакетов, SOCKS5, политики и конфигурационная схема. Windows реализует установку и управление службой, локальный IPC, файловые гарантии, TUN и зависящие от ОС сокеты и маршруты.
- **Отдельный Go-клиент для Windows.** Даёт свободу реализации, но дублирует меню и сетевые политики; обновления Linux и Windows будут расходиться.
- **WSL или только SOCKS5.** Не дают нативного интерфейса Windows с VPN-IP и полного поведения фоновой службы и P2P.

## Контракт для пользователя

- Запуск без аргументов открывает тот же TUI: установка, изменение настроек, управление и состояние службы, список режимов, все 13 SOCKS5-портов, маршруты, peer settings и обновление. Те же формы, порядок, клавиши, скрытый ввод импорта, показ и ротация SOCKS5-учётных данных. Только текст, привязанный к ОС, адаптируется. Сохранить CLI установки и foreground-режимы, в том числе `-no-tun` с его нынешними ограничениями.
- Настроенная служба запускается при старте системы, не зависит от терминала. Её можно запустить, остановить, перезапустить, удалить и установить из того же меню. Конфигурация и защищённый контроль доступны локальным администраторам и службе. Не открывать TCP-порт управления и не передавать секреты через аргументы службы, окружение или журнал.
- Порты 1080–1089 сохраняют текущее соответствие всем десяти режимам: AWG и TLS через extended/request-piece по TCP и µTP плюс нативные AWG и WG по UDP. Прямое подключение к хабу и DHT-поиск сохраняются там, где предусмотрены. Не менять режим на другой при ошибке. Порты 1090–1092 — Failover, Round-robin, Adaptive. Сохранить TCP/UDP, DNS хаба, отдельные egress-выборы, собственные пулы, резервирование выключенных портов и закрепление начатых сессий. Windows-клиент как потребляет, так и обслуживает назначенный egress в соответствии с настройками и разрешениями хаба.
- Один настоящий Windows TUN получает импортированный IPv4 из общей группы, MTU и маршруты. Windows-приложения обращаются к хабу и другим VPN-IP без SOCKS5; при разрешении хабом узлы могут открывать соединения к сервисам на VPN-IP Windows. Обычный трафик не получает VPN default route; только SOCKS5 и другие явно overlay-сокеты пользуются туннельным выходом. Основной режим TUN выбирается по тем же правилам. Переключение режимов не пересоздаёт TUN.
- Для P2P сохранить десять режимов, отдельные входящие и исходящие направления, три P2P-пула, глобальные правила, индивидуальные переопределения, изменения на ходу, разрешения и отзыв хабом. Сохранить отдельные TCP/UDP-кандидаты, UDP hole punching, ручные публичные адреса и автоматическое обнаружение шлюза для PCP, NAT-PMP и UPnP IGD. Релей через хаб работает только по текущим правилам обеих сторон; при запрете релея нет тихой подмены прямого канала. Достижимость по-прежнему зависит от NAT и firewall; режимы не отключают Windows Firewall и не открывают всё подряд.

## Платформенные границы

### Служба, TUI и обновление

Сохранить общий код `cmd/btawg-client` и `internal/service` для меню, действий и форм; системные реализации разделить по целевым файлам. `go-tui` уже содержит Windows-консольный backend; меню не переписывается. Windows Service Control Manager запускает тот же бинарник под LocalSystem в служебном режиме и получает готовность после локальной инициализации, не после достижения хаба. Остановка отменяет общий managed daemon и дожидается очистки. Сохранить автозапуск, переключение на ручной старт без запрета запуска и восстановление после сбоя. Удаление службы останавливает её, но сохраняет установленный клиент и рабочую конфигурацию для повторной установки, как на Linux. Не перезаписывать чужую службу с конфликтующим именем. **View service logs** показывает записи Windows Event Log. Инсталляция и управление — из повышенного терминала, аналогично `sudo` на Linux; статусы и ошибки остаются видимыми в TUI. Linux-сервер остаётся на systemd.

Защитить установленный бинарник и DLL в Program Files, конфигурацию в ProgramData и локальный named pipe правами Administrators/SYSTEM. Отвергать удалённые подключения и захват имени pipe; до отправки запросов проверять, что PID сервера pipe совпадает с PID службы из SCM. Ошибка проверки, доступа или занятая служба не переводят клиент в офлайн-режим. Офлайн-запись только для подтверждённо остановленной или неустановленной службы; согласовать запись с запуском так, чтобы служба не прочитала устаревший конфиг. Файлы пишутся атомарно с сохранением защиты, включая путь из временного файла. Отладочный foreground не выдаёт себя за управляемую службу.

Windows-артефакт — ZIP с `btawg-client.exe`, официальной подписанной amd64 `wintun.dll` и лицензией Wintun. Фиксировать и проверять дайджест источника DLL; загружать DLL из доверенного места рядом с исполняемым файлом, а не из произвольной рабочей директории. Публиковать контрольную сумму ZIP в `SHA256SUMS`. Обновление из TUI использует тот же канал стабильных релизов, прямое соединение и проверку контрольной суммы. Прогресс и отмена доступны до передачи операции отдельному процессу; если запущенный TUI блокирует замену `.exe`, он завершает работу перед заменой и показывает результат при следующем открытии. Не делать активным частично заменённый комплект: пережить прерывание обновления без запуска смешанной пары EXE/DLL. Сохранить конфигурацию, автозапуск и предыдущее состояние запущена/остановлена, дождаться локальной готовности при запуске и откатить комплект на ошибке. Не подменять обновление инструкцией скачать вручную.

### TUN, прокси и транспортные сокеты

Использовать Windows-бэкенд Wintun из уже подключённого `amneziawg-go`; настраивать адаптер по его LUID, адрес, MTU и IPv4-маршруты штатным IP Helper. Отдельные ОС-реализации нужны для открытия адаптера, локальной идентификации сокета, его привязки, carrier TCP options и обнаружения физического шлюза. Вынести общий `sharedTUN` и логику владения потоком из Linux-only файлов там, где они не зависят от ОС. Сохранять закрепление сокета за путём до отправки первого пакета и освобождение ресурсов после закрытия. Создание и очистка не меняют чужие адаптеры, адреса, маршруты и правила.

Различать свой адаптер и совпадение по имени: проверять ожидаемую идентичность до применения настроек, не переиспользовать чужой TUN и не удалять его состояния при ошибке. При поиске физического шлюза, выборе источника и публикации локальных P2P-кандидатов не считать Wintun обычным uplink. При изменениях сети проверять актуальность выбранного физического интерфейса и источника; нельзя отправлять внешние управляющие и туннельные пакеты обратно через overlay.

Для Windows выбран userspace netstack для явно overlay-клиентских TCP/UDP-сокетов (SOCKS, DNS, probes, исходящие overlay control/egress-запросы), а Wintun — для системных приложений и входящих overlay-слушателей. У Windows нет поддерживаемого аналога Linux `ip rule oif` с отдельной таблицей; `IP_UNICAST_IF` сам по себе не создаёт маршрут, а высокая метрика TUN `/0` не изолирует трафик при исчезновении физического default route. Не менять default route и не использовать зарезервированные системные API.

Общий диспетчер различает владельцев VPN-потоков: исходящий сокет netstack получает эксклюзивный источник из пространства портов ОС, закрепляет поток за своим транспортом до первого пакета, а входящие ответы идут владельцу вместо инъекции в Wintun. Принимающие overlay-слушатели и обычные системные приложения остаются на Wintun. План должен доказать отсутствие коллизий между несколькими transport paths и сокетами ОС, включая wildcard bind, освобождение/повторное использование портов, TCP/UDP, IPv4-фрагменты и ICMP-ошибки. Неиспользуемые режимы не поднимают собственные драйверы/адаптеры. Конкретное размещение netstack и механизм резервирования портов определяются в реализации после узкой проверки на Windows.

Первый сетевой критерий — одновременно TCP/UDP прокси на произвольный IPv4 идёт через выбранный туннель; обычный TCP/UDP к тому же адресу не идёт через TUN, включая исчезновение исходного default route; внешние carrier-, DHT- и P2P-сокеты не зацикливаются в TUN. Нельзя получить видимость паритета изменением default route, отключением защит Windows или заменой рабочего режима заглушкой.

### Проверка и выпуск

- Кросс-сборка Windows x64 без CGO, сборка Linux и проверка существующих сценариев, но кросс-сборка не считается сетевой проверкой. Для автоматических Windows-проверок использовать GitHub-hosted Windows x64 с административными правами; проверять фактическую загрузку Wintun. Межмашинные сценарии, перезагрузку и настоящий TUI проверять на Windows x64 VM с Linux-хабом и Linux-пиром. Выпуск Windows ZIP блокируется до smoke на точном комплекте с тем же SHA-256, который публикуется. При первом выпуске обновление и откат проверяются с двумя версиями и контролируемым тестовым источником релиза без изменения production-источника.
- Проверить настоящий TUI в повышенном Windows Terminal на обеих целевых версиях Windows: установка, запуск без открытого TUI/после перезагрузки, сохранение и перестарт, живые переключения режимов и пулов, скрытая вставка импорта, выбор мышью и клавиатурой, Ctrl+T и копирование credentials, все настройки пиров и egress, просмотр логов, удаление, обновление и восстановление после срыва обновления.
- На Windows↔Linux проверить TCP/UDP через каждый режим, DHT для поддерживающих режимов, все три балансера при потере/возврате пути, DNS и выбранный egress, неизменный VPN-IP, доступ в обе стороны и маршруты до/после stop и при потере физической сети. Проверить сохранение существующих сессий там, где это гарантирует Linux, отказ без доступного пути, отсутствие выхода в обход туннеля и неприкосновенность обычного Интернета. Для P2P — направления, все типы транспортов, политики и пулы, прямое и релейное соединения, отзыв разрешения, ручные кандидаты и обнаружение/удаление поддерживаемых NAT-мэппингов в контролируемой сети.

Готовность означает работу всего контракта на Windows, а не только успешное появление `.exe`. Что не проверено на настоящей Windows, не объявлять подтверждённым.
