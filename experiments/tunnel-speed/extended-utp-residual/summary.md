# Extended/µTP: residual application pauses and useful throughput at 1% loss

**Decision:** keep the previous transport fix; no new default, RTT algorithm, or pacing-floor change from this investigation. For an operator with a measured, sufficiently fast WAN, the existing explicitly configured pacing mode can materially improve delivery. Its cap must not be confused with available bandwidth. A mid-session change from LAN to WAN and a connection already opened at WAN RTT behave differently.

## Which layer was idle?

The original `repeat.final.47032` from the [previous experiment](../extended-utp-path-step/summary.md) recorded eight complete zero-delivery seconds, +8.97 through +16.97 s after the change. Across the nearest queue samples the underlay still sent 41,886 bytes down and 30,302 up, with two downlink netem drops; the inner sender recorded one TCP retransmission, no newly ACKed bytes, and no **new** hub engine queue drop during the interval. That trial had no µTP sequence trace: one eight-second outer timeout cannot be inferred from it.

Fresh header-only traces captured both TUN endpoints, the oldest outer send, cumulative ACK, RTO and retries. In `trace.wan.47032`, the client received 39,296 inner TCP payload bytes in seconds +6 to +16; **all were beyond the missing cumulative ACK edge**, so none could advance the stream. The outer oldest sequence advanced from 42710 to 42757. One DATA (42742) timed out, but this did not explain the entire pause. During much of it cwnd was one 1,382-byte segment. In `trace.ok.47011` there was an 18-second zero-progress streak, no hub µTP RTO during that streak, and 341,384 inner TCP bytes arrived ahead of their ACK edges during seconds +6 to +21. The hub engine dropped 481 packets in the initial five-second burst, none in that subsequent plateau. In a separate run `droptrace.wan.47032` the missing byte for one actual flow matched a hub queue rejection at +0.607 s (TCP edge 1751063737); two later sends containing the edge were observed on the hub TUN but the edge did not appear at the client before capture ended. During a later three-second stall 158,412 bytes beyond the edge did arrive. This identifies one specific loss site, not the fate of every retransmission or every stalled flow. Another drop-traced run had no multi-second stall. Capturing headers changes scheduling; seeds fix netem configurations, not which sequence numbers get dropped. **Eight seconds was an observation, not a bound.**

There is also an RTT estimation issue. The sender updates the filter for every newly ACKed original, including thousands of previously stalled originals exposed by cumulative ACK progress. In the traced transition ACK ages >600 ms were sampled 11,451 times by +5.7 s; physical RTT remained ~200 ms. The hub's RTO temporarily exceeded 10 s. A deterministic coalesced-ACK test reproduced an SRTT of 3,483 ms and no retry by 1.5 s. The experimental `rtt` arm took one sample per ACK arrival (latest newly acknowledged, never retransmitted DATA); the deterministic test and two existing loss/MTU tests passed. It shortened the longest application stall to 1 s in both live trials but **reduced** late receiver goodput to 0.246/0.367 Mbit/s versus 0.704/0.403 for matched baselines. Not adopted as a speed fix. In late unpaced windows the combination of small outer flight, repeated fast-loss backoff, slow ACK-driven regrowth, serial frame delivery and missing inner ranges limits useful throughput; neither FEC nor a single RTO constant explains it.

## Throughput controls

Real Linux hub and client, `socks5-awg-ext-utp`, eight CUBIC download flows, 44 s per trial, fixed CPU affinities, MTU and offloads as in the previous experiment. Except `cold`, the change occurs at +5 s of running traffic. `wan`: previously clean LAN → 100 ms per direction and independent 1% loss. `prewan`: 100 ms per direction before handshake, then 1% loss applied to the live path. `cold`: same WAN delay **and loss** already in force before handshake; the +5 s marker only aligns measurement windows. Late goodput is a ten-second TCP receiver window beginning at the first full second at least 24 s after the marker; `post_mbps` uses all 38 complete seconds. Zero intervals are not filled-in timeouts. Pacing is per endpoint, applied before startup to the same two binaries; initial baseline refers to the preceding working-tree candidate, not v0.14.4. No external peer or public DHT traffic is required.

| Late receiver Mbit/s, seeds 47011 / 47032 | Unpaced | Existing pacing 50 Mbit/s | Existing pacing 200 Mbit/s |
|---|---:|---:|---:|
| Live LAN → WAN + loss | 0.704 / 0.403 | 1.045 / 1.472 | 1.321 / 1.436 |
| Already WAN → loss only | 0.964 / 0.622 | 18.890 / 23.135 | not run |
| Fresh connection on existing WAN loss | 0.805 / 0.743 | 19.540 / 20.058 | not run |

With 50 Mbit/s pacing after the LAN→WAN step there were 0/1 consecutive zero seconds, versus 3/4 on the same unpaced seeds; **whole** post-change goodput was lower (1.60/1.50 vs 1.97/1.71) because the unpaced path delivers a larger initial burst. Clean LAN whole-window goodput was 328.48 unpaced vs 22.01 Mbit/s with pacing at 50. This is not a universal recommendation. The current option also changes loss recovery and window growth; its A/B does not isolate packet scheduling alone.

## Why not force a larger window?

The paced window can refill toward 90% of configured pacing rate × minimum RTT only when the forward delay estimate is below target/8. A low old RTT minimum can survive the route step. With identical pacing at 50 and the same confirmation guards, the `early` (16 MSS eligibility only) arm reached 1.67/1.40 Mbit/s; `delay-only` (more forward rebase) reached 1.73/1.34. `rttbase-only` (refresh minimum RTT at confirmed step, retaining normal forward pressure) reached 19.03/20.81 in those trials. `paced-step` (refresh both) reached 17.43/16.65; neither full-second stalls nor AWG parity were observed in those two runs. Using only the changed hub got 17.24 in one download control. The `optin` variant kept the eligibility change local to configured pacing. Its second, independent comparison varied widely: 2.70/16.74. These are **lab arms**, not production recommendations.

A separate **10 Mbit/s upstream-of-netem TBF with a 32,000-byte FIFO** and a concurrent direct CUBIC connection distinguished overflow from the injected 1%. With `paced-step` vs existing pacing at the same 50 Mbit/s cap, extra FIFO drops during seconds +4…+32 rose **16 → 23,496** and **0 → 18,995** across seeds; CUBIC goodput fell **0.758 → 0.158** and **1.23 → 0.410 Mbit/s**. Physical p95 rose to 225 ms. An alternative limiting BDP credit growth to a fraction of newly ACKed bytes (`clocked`) gave only 3.91–4.32 solo and still lost substantial CUBIC throughput on one seed. Even the conservative `optin` variant produced **17,797** FIFO drops in the +4…+32 s window and 0.505 Mbit/s for CUBIC on a repeated narrow-path trial; the same build/seed sometimes did not trigger and made no late FIFO drops. The isolated `capacity` trial adds the limiter and a 16 s competing TCP stream 18 s *after* introducing loss and delay; it is not pooled with `shared`. These results rule out assuming configured sender rate is deliverable bottleneck capacity. A useful next discriminator is a bounded rate/credit probe that requires observed delivered-rate growth before increasing the budget and retracts it on rising queue delay, tested against real CUBIC at several bottleneck rates.
